# 管理画面 一覧UI・MUI DataGrid 導入評価 v1.0

**Version**: 1.0  
**作成日**: 2026-02-12 00:29  
**更新日**: 2026-07-06 16:50:15  
**関連**: `ADMIN_MUI_MIGRATION_PLAN_v1.0.md` Phase 5、`ADMIN_UI_FIT_GAP_v1.0.md`、`REMAINING_TASKS_PLAN_v1.0.md`（**#16** UI-P5-POC）  
**目的**: 「MUI DataGrid を導入するか」「導入するならどの画面からか」を意思決定するための比較表と方針案をまとめる。実装は行わない。

## 1. 背景と目的

### 1.1 背景

- 管理画面は MUI 方針（Phase 0〜4 完了：ThemeProvider、DatePicker、Dialog、FormField、Button/Card/Icons の段階統一済み）。
- 一覧ページ（Resources / Customers / Menus / Bookings）は、現状それぞれ独自の表・カード・リスト実装が混在している。
- Phase 5 として「一覧系の検討」が計画にあり、DataGrid 適用可否の判断と FullCalendar（予約タイムライン）との役割分担を明確にする必要がある。

### 1.2 目的

- MUI DataGrid（**無償版＝Community 版**）を前提に、導入メリット・デメリット・移行コストを整理する。
- 導入する場合の方式案（標準採用 / 段階導入 / 非採用）を比較し、現時点の推奨案と次の一手を明示する。

### 2.3 補足（根拠コード）

- **ResourcesPage**: `resourceApi.getList({ sort: 'type,sort_order,name' })` で全件取得。`filteredResources` はクライアント側で `searchTerm` / `typeFilter` / `statusFilter` によりフィルタ。表示は `ResourceCard` の grid。
- **CustomersPage**: `customerApi.getList(filters)` に `page`, `per_page: 20`, `search`, `status` を渡しサーバページング。表示は `CustomerCard` の grid。`Card.Footer` で前へ/次へ。
- **MenusPage**: `menuApi.getList(filters)` に `page`, `per_page`, `search`, `category`, `is_active` を渡しサーバページング。`viewMode === 'grid'` でカード、`'list'` で `<table>` + `MenuTableRow`。ページネーションは前へ/次へ。
- **BookingsPage**: `bookingApi.getList(filters)` に `page`, `per_page: 100`, `search`, `status`, `date`, `sort` を渡しサーバページング。`viewMode === 'list'` は日付ごとにグループしたカード内リスト、`'timeline'` は `BookingTimelineView`（FullCalendar ベース）。

## 3. DataGrid の概要（無償版＝Community 前提）

### 3.1 できること（標準機能）

- ソート（列ヘッダークリック）、フィルタ（列フィルタ）、ページング（クライアント/サーバ両方のパターン対応）。
- 行選択、セル編集（編集可能モード）、テーマ/スタイルのカスタマイズ。
- 列の定義（columns）と行データ（rows）の明確な API。仮想化により大量行でも描画負荷を抑えやすい。
- キーボード操作・フォーカス管理が組み込まれており、アクセシビリティの向上が期待できる。

### 3.2 できない／弱いこと（無償版の制限・カスタムが必要な点）

- **Pro のみ**: 高度なフィルタ UI、列ピン・列/行のドラッグ並び替え、ツリーデータ、行グループ＋集計、Excel エクスポート、高度な仮想化など。
- 無償版でも「表形式」が主であり、**カード型 UI** や **タイムライン** は DataGrid の用途外。予約の「日付グループ＋リスト」や Timeline は現状のまま別コンポーネントが適切。
- 既存の「カード grid」表示を DataGrid に寄せる場合は、表形式に切り替えるか、DataGrid とカードを併用する設計が必要。

### 3.3 移行コスト・影響

- **実装**: 各一覧で rows/columns 定義、API レスポンスのマッピング、ページング/ソート/フィルタを DataGrid の props に合わせる作業。
- **既存 UI**: カード表示をやめて表に統一するか、画面ごとに「表のみ」「カード＋表」を決める必要あり。
- **データ取得 API**: サーバページング・ソート・フィルタをすでに持つ画面（Customers / Menus / Bookings）は API は流用しやすい。Resources は現状全件取得のため、ページング API を追加するか、クライアントページングに寄せるか検討。
- **テスト・ドキュメント**: 一覧の仕様が変わるため、テストケースと画面仕様の更新が必要。

### 3.4 tugical 管理画面として重要な観点

- **業務効率**: ソート・フィルタ・検索が統一されると操作パターンが揃い、習得しやすい。
- **操作統一**: MUI 方針と合わせて一覧も MUI に寄せると、見た目・挙動の一貫性が高まる。
- **学習コスト**: DataGrid は API が明確なため、AI 駆動開発や新規メンバーでも「どの props で何をするか」が分かりやすい。
- **将来 SaaS／マルチテナント**: テナントごとのデータ量増加に備え、サーバページング＋仮想化があると安心。無償版でも基本的なページング・ソートは利用可能。

## 4. 判断軸

以下の軸で「DataGrid を導入するか」を比較する。

| 判断軸 | 内容 |
|--------|------|
| **UX** | 一覧の操作性（ソート／フィルタ／検索／ページング）が統一され、分かりやすいか。 |
| **開発効率** | AI 駆動開発のしやすさ（明確な API／props 構造）。 |
| **保守性** | バグの入りにくさ、標準化による変更の局所化。 |
| **パフォーマンス** | 件数増加時の耐性（仮想化・サーバページング）。 |
| **カスタマイズ性** | tugical らしい見せ方（カード／タイムライン等）が可能か。 |
| **依存・ライセンス** | 無償の範囲で成立するか（Community は MIT）。 |
| **移行コスト** | 段階導入できるか、影響範囲と工数。 |

## 5. 方式案（A/B/C 比較表）

### 5.1 案 A：DataGrid を標準採用（一覧は原則 DataGrid）

| 項目 | 内容 |
|------|------|
| 概要 | 一覧は原則 MUI DataGrid に統一。カード UI が必須な画面のみ例外。 |
| 対象 | 全一覧（Resources / Customers / Menus / Bookings の「表として見せるビュー」）。 |
| 例外 | 予約の **Timeline** は FullCalendar のまま。顧客・メニュー・リソースの「カード表示」は廃止するか、表示切替で「表／カード」の両立を検討。 |
| UX | ◎ ソート・フィルタ・ページングが統一。 |
| 開発効率 | ◎ DataGrid の API で統一。 |
| 保守性 | ◎ 一覧ロジックが DataGrid に集約。 |
| パフォーマンス | ◎ 仮想化・サーバページングで件数増に強い。 |
| カスタマイズ性 | △ 表形式中心。カードは別コンポーネントが必要。 |
| 移行コスト | × 全一覧の書き換えが必要。カード廃止なら影響大。 |

### 5.2 案 B：段階導入（優先画面から DataGrid 化）

| 項目 | 内容 |
|------|------|
| 概要 | 優先 1〜2 画面で DataGrid を導入し、他は現状維持→リファクタ時に置換。 |
| 優先候補 | **MenusPage（list ビュー）**：既に `<table>` があり、サーバページング・フィルタも実装済み。列定義が明確で DataGrid に寄せやすい。次点で **CustomersPage**（カードを「表」にした場合の候補）。 |
| 根拠 | メニューは「表で比較したい」ニーズが高く、既存 list モードを DataGrid に差し替えるだけで UX 向上が見込める。顧客は件数増加時に表＋ページングのメリットが大きい。 |
| UX | ○ 優先画面で向上、他は現状維持。 |
| 開発効率 | ○ 優先画面から DataGrid のパターンを確立。 |
| 保守性 | ○ 混在期間はあるが、範囲を限定できる。 |
| パフォーマンス | ○ 導入画面で改善。 |
| カスタマイズ性 | ○ 他画面は従来のカード/リストを維持可能。 |
| 移行コスト | ○ 1〜2 画面に限定でき、PoC としても実施しやすい。 |

### 5.3 案 C：DataGrid は採用しない（現状の UI を整える）

| 項目 | 内容 |
|------|------|
| 概要 | DataGrid は使わず、共通の Table／Sort／Filter コンポーネントを自作するか、MUI Table（`<Table>`）で統一。 |
| 対象 | 全一覧を現行のまま、見た目と挙動を MUI Table や共通コンポーネントで揃える。 |
| UX | △ ソート・フィルタは自前実装のため画面ごとに差が出やすい。 |
| 開発効率 | △ 共通化の設計・実装が必要。 |
| 保守性 | △ 自作のためバグや仕様ブレのリスク。 |
| パフォーマンス | △ 仮想化などは自前で対応する必要。 |
| カスタマイズ性 | ◎ カード／表／タイムラインを自由に組み合わせ可能。 |
| 移行コスト | ○ 既存を活かしつつ MUI Table に寄せる程度なら比較的軽い。 |

## 6. 結論と次アクション

### 6.1 現時点の推奨案

**案 B：段階導入（優先画面から DataGrid 化）** を推奨する。

### 6.2 推奨理由（3 点）

1. **リスクと効果のバランスが良い**  
   全一覧を一度に DataGrid にすると移行コストとカード廃止の影響が大きい。MenusPage の list ビュー（既存 `<table>`）から DataGrid に差し替えることで、少ない変更でソート・フィルタ・ページングの UX 向上と、DataGrid の習熟が同時に得られる。

2. **既存 API と相性が良い**  
   MenusPage はすでにサーバページング・検索・フィルタ（カテゴリ・ステータス）を利用しているため、DataGrid の「サーバサイドモード」に載せやすい。CustomersPage も同様に、表ビューを追加する場合の次の候補にしやすい。

3. **将来の拡張方針を残せる**  
   案 B で 1〜2 画面の実績を積んだうえで、他画面を DataGrid に寄せるか、あるいは案 C のように MUI Table で整えるかを、改めて判断できる。

### 6.3 次の一手

- **PoC を実施する場合**  
  **MenusPage の list ビュー** を MUI DataGrid（Community）に置き換える PoC を 1 タスクとして実施する。  
  - 内容：`menuApi.getList` をそのまま利用し、rows/columns を定義、ページング・ソート・フィルタを DataGrid の props に接続する。  
  - 成果物：MenusPage の「リスト表示」が DataGrid で動作する状態。grid カード表示は当面維持。  
  - 判断：PoC の結果を見て、他画面への展開可否を Phase 5 の続きで決定する。

- **PoC を実施しない場合**  
  Phase 5 は「検討完了・方針のみ文書化」とし、一覧の共通化は「MUI Table ベースの共通コンポーネント検討」や「現状維持のまま a11y・キーボード操作の改善」など、軽い改善に留める。
