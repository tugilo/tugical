## 1. 結論（総合判定）

**現状は「マニュアルレス可」ではない。**  
ナビ・ログイン・設定ウィザード・ダッシュボード空状態の文言など、良い下地はあるが、**電話予約・予約の変更/キャンセルという主業務が画面だけで完結しない**。

| 領域 | 判定 | 一言 |
|------|------|------|
| ログイン | マニュアルレス可に近い | ラベル・店舗・テスト入力が明確 |
| ダッシュボード（閲覧） | 補助説明があれば可 | 相棒メッセージは良いが次アクション不足 |
| 予約の新規作成 | **マニュアル必須** | 「旧」「複数」の二重 CTA、モバイルタイムライン依存 |
| 予約の変更・キャンセル | **マニュアル必須（実質不可）** | 一覧クリックが TODO（詳細未実装） |
| 顧客・メニュー | 補助説明があれば可 | CTA・カード操作は概ね分かる |
| リソース | 補助説明があれば可 | 「リソース」語＋内部コード見出しが障壁 |
| 設定（LINE） | マニュアルレス可に近い | 1→4 ウィザードが優秀 |
| ロール分離 | Fail | staff でも設定ナビ・画面に入れる |

## 2. 評価方法（要約）

PLAN の観点 U1〜U6 とケース C01〜C12 に従い、ブラウザ操作で判定。

| 記号 | 意味 |
|------|------|
| Pass | マニュアルなしで達成できる |
| Partial | 迷うが到達可能、または軽微な誤解リスク |
| Fail | 主操作が阻害、または誤解で誤操作しうる |

優先度: **P0** 主業務停止 / **P1** 初見阻害 / **P2** 慣れれば可 / **P3** 微修正

## 3. ケース別判定

| Case | シナリオ | 判定 | 根拠（観察） |
|------|----------|------|----------------|
| C01 | 未認証→ログイン | **Pass** | `/admin/login` へ誘導。店舗・メール・パスワードが明確。ローカルではテスト用「入力」ボタンあり |
| C02 | ログイン直後の次の一手 | **Partial** | 「今日は予約がありません…」は分かりやすい。一方 **新規予約への導線なし**。要対応 0 件時に「何をする画面か」は分かるが「何をすべきか」は弱い |
| C03 | 電話中の新規予約 | **Fail** | 「新規予約（旧）」と「✨ 複数メニュー予約」が並び、初見でどちらを使うか不明。複数メニューモーダル自体は顧客→日時→メニューの流れは良いが、**主 CTA が分裂** |
| C04 | 今日の予約確認 | **Partial** | ダッシュボードは今日 0 件で明確。予約管理は週タイムライン既定でモバイルでは密集。リストは日付グループで読みやすいが **14:00−14:00 / メニュー未設定** が信頼性を損なう |
| C05 | 変更・キャンセル | **Fail** | リスト行クリックは `handleBookingClick` が **TODO（console.log のみ）**。詳細・編集・キャンセル UI に到達できない |
| C06 | 新規顧客 | **Pass** | 「新規顧客登録」が目立つ。検索・ステータスも直感的。カードに明示的な編集ボタンは見えにくいが登録導線は十分 |
| C07 | メニュー追加・編集 | **Pass** | 説明文・「新規メニュー」・詳細/編集/削除がカード上にあり、削除は確認ダイアログ前提 |
| C08 | リソース追加 | **Partial** | ナビ副題「スタッフ・設備」は良いが、画面見出しは「リソース」。カード見出しが `room` / `atsushi` / `test`（内部キー）で、表示名が副情報になっている |
| C09 | 設定（LINE） | **Pass** | 「LINE 連携：未設定」＋ 1→4 ステップ。専門用語に日本語補足あり。マニュアルレス志向として最良クラス |
| C10 | ナビだけで辿れる | **Pass** | 各項目に短い説明付き。モバイルはハンバーガー必須だがラベルは明瞭 |
| C11 | 0 件空状態 | **Partial** | ダッシュボード空文言は優秀。ただし **「予約を作成」等の CTA がない**。予約一覧はデータありのため空状態は未確認 |
| C12 | 権限外操作 | **Fail** | 仕様は設定＝owner のみ想定だが、**staff でも「設定」ナビ表示・画面表示・フォーム閲覧が可能** |

## 5. ケース別「あるべき使い方」と現状ギャップ

### 5.1 受付が電話を受けたとき（最重要）

**あるべき流れ（マニュアルレス）**

1. ログイン済み → ダッシュボードまたは予約管理を開く  
2. 「新規予約」1 ボタン  
3. 電話番号/名前検索 → なければその場で顧客作成  
4. メニュー（1つ以上）→ 日時 → 担当任意 → 確定  
5. 一覧に即反映、必要ならキャンセル/変更は同じ詳細から

**現状ギャップ**

- 新規が 2 ボタン（旧 / 複数）  
- 顧客新規は別画面（顧客管理）へ行く必要があり、電話中の往復が増える  
- 確定後の変更・キャンセル経路がない（P0-1）

### 5.2 朝イチで今日の準備をする（オーナー/スタッフ）

**あるべき**

1. ダッシュボードで今日件数・次の予約・要対応  
2. 各項目から予約詳細へ 1 クリック  
3. 空なら「予約を取る」or「準備完了」が分かる

**現状ギャップ**

- メッセージは良いが詳細導線・作成 CTA が弱い  
- 要対応の中身が「pending_today」中心で、業務語としての説明が薄い（現状 0 件のため文言のみ確認）

### 5.3 初回店舗セットアップ（オーナー）

**あるべき**

1. ログイン → 設定ウィザードで LINE  
2. メニュー・リソース（スタッフ）を登録  
3. 試し予約

**現状ギャップ**

- 設定ウィザードは **Pass 水準**  
- リソース語彙と内部コード表示が初回の障壁  
- メニューは比較的分かりやすい

## 6. 画面別サマリ

| 画面 | マニュアルレス度 | 強み | 弱み |
|------|------------------|------|------|
| ログイン | 高 | 明確なラベル、店舗選択、（ローカル）入力補助 | 本番でのテスト情報露出リスク |
| ダッシュボード | 中 | 相棒メッセージ、3 ブロック構成 | 行動 CTA 不足、詳細未接続 |
| 予約管理 | 低 | 検索・フィルタ・リストの日付グループ | 二重 CTA、詳細 TODO、表示バグ、モバイル TL |
| 顧客管理 | 中〜高 | 新規 CTA、検索 | カード操作の明示性、回数表示の正確性 |
| メニュー管理 | 高 | カード上の詳細/編集/削除 | UI スタック混在 |
| リソース管理 | 中 | タイプ別集計 | 「リソース」語、内部コード見出し |
| 設定 | 高 | ステップウィザード | ロールガード不足 |

## 7. 推奨改善順序（次 Phase 候補）

実装は本 Phase の Scope 外。着手するならこの順を推奨する。

1. **P0-1** 予約詳細・変更・キャンセルを実装（電話運用の最低条件）  
2. **P0-2 / P0-3** 新規予約 CTA の一本化＋ダッシュボード導線  
3. **P1-1 / P1-2** 一覧の時刻・メニュー表示の正しさ  
4. **P1-3** モバイル既定ビューをリストに  
5. **P1-4** 設定のロールガード  
6. **P1-5** リソース表示名ファースト  
7. P2 以降（用語・UI 統一・通知ラベル）
